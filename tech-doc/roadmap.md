# Web 3D 多人卡丁車遊戲｜分階段技術規格與驗收計畫

> 文件版本：1.1｜更新日期：2026-09-27  
> 技術基礎：Next.js（App Router）、React、TypeScript、React Three Fiber、Drei、Rapier、Node.js、Colyseus  
> 產品方向：原創、卡通化 Arcade Kart Racing；電腦／電視作為主要遊戲畫面，玩家掃描 QR Code，以手機作為控制器。  
> 進度來源：Phase 1、2 已於 2026-09-26 完成；Phase 3 程式與自動驗收於 2026-09-27 完成，iOS／Android 真實裝置人工驗收仍待執行。

---

## 0. 產品範圍與共同技術原則

### 0.1 最終產品

- 網頁直接開啟的完整 3D 卡丁車遊戲，使用原創角色、車輛、賽道、音效與圖像素材。
- Host 在電腦上建立房間；其他玩家使用手機掃描 QR Code 加入，手機僅需開啟瀏覽器。
- 支援 **2–4 人**同場，主畫面採用可追蹤所有玩家的共用攝影機；分割畫面為後續擴充項目。
- Arcade 駕駛手感：加速、煞車、轉向、漂移、Mini Turbo、碰撞反彈與 Spin Out；不做擬真汽車物理。
- 完整比賽循環：大廳 → 準備 → 倒數 → 比賽 → 排名 → 結算 → 再來一場。
- 第一個可供朋友玩的多人 MVP 以 Phase 4 為里程碑；道具與正式美術分別在 Phase 5、6 完成。

### 0.2 技術與部署決策

| 層級      | 技術                                           | 職責                                                |
| --------- | ---------------------------------------------- | --------------------------------------------------- |
| 網站與 UI | Next.js App Router + React + TypeScript + CSS  | 首頁、Host 遊戲頁、大廳、手機控制器、HUD            |
| 3D 渲染   | React Three Fiber、Three.js、Drei              | 車輛、賽道、第三人稱攝影機、粒子與場景              |
| 物理      | Rapier 3D                                      | 碰撞體、感測區、基礎運動及碰撞偵測                  |
| 遊戲核心  | Framework-independent TypeScript               | 固定時間步長、玩家輸入、Arcade 駕駛、漂移、賽事規則 |
| 即時連線  | Node.js + Colyseus + WebSocket                 | 房間、玩家、輸入轉送、權威遊戲狀態與同步            |
| 3D 資產   | Blender → GLB / glTF                           | 原創卡丁車、角色、賽道與動畫                        |
| 測試      | Vitest、Playwright、伺服器整合測試             | 遊戲邏輯、頁面流程、多玩家與回歸測試                |
| 部署      | Next.js 靜態／應用主機 + 獨立常駐 Node.js 主機 | 網站與需要長連線的遊戲伺服器分開部署                |

**重要邊界**：`app/` 只放頁面與介面；目前 3D 渲染放 `game/components/`；不依賴 React 的模擬與規則放 `game/core/`；Rapier 整合放 `game/physics/`；輸入裝置放 `game/input/`；多人通訊放 `game/network/`。不要將所有遊戲邏輯塞進 `Game.tsx`。

**多人架構遷移**：Phase 1–2 先用本機遊戲模擬；Phase 3 由 Colyseus 建立房間並轉送單人手機輸入，Host 暫時持有模擬狀態；Phase 4 將模擬移至權威遊戲伺服器，以同一套純 TypeScript 遊戲核心降低重寫成本。

### 0.4 建議目錄（可依既有專案調整，不必為了改目錄重寫程式）

```text
src/
├── app/
│   ├── page.tsx
│   ├── game/page.tsx                  # Host 遊戲畫面
│   ├── room/[roomId]/page.tsx         # 房間大廳
│   └── controller/[roomId]/page.tsx   # 手機控制器
├── game/
│   ├── core/                         # 無 React 相依的遊戲邏輯
│   │   ├── kart/
│   │   ├── collision/
│   │   ├── race/
│   │   └── items/
│   ├── rendering/                    # R3F 元件、鏡頭、特效
│   ├── input/                        # Keyboard / Touch / Tilt adapters
│   ├── network/                      # Socket client、狀態插值
│   ├── assets/                       # 模型與資產宣告
│   └── Game.tsx                      # 場景組裝，避免塞入業務規則
└── components/                       # 共用網站 UI
server/
├── rooms/RaceRoom.ts
├── state/
├── systems/
└── index.ts
```

後續如採 monorepo，可將共用遊戲核心、輸入型別及網路訊息協定抽至 `packages/shared/`；不應讓 Node.js 伺服器直接依賴瀏覽器專用模組。

# Phase 3｜手機控制器與房間

**狀態：程式與自動驗收完成；P3-T08 及真實 iOS／Android 人工驗收待執行。**

## 1. 階段目標

讓 Host 在電腦上開啟遊戲，透過建立房間取得 QR Code，手機掃碼後能以觸控控制**一台車**。驗證跨裝置連線與控制延遲，再進入真正多人同步。

# Phase 4｜2–4 人即時多人賽車

## 1. 階段目標

將遊戲模擬轉為伺服器權威，支援同一房間 2–4 人使用各自手機操控；Host 主畫面顯示所有車輛、碰撞、進度與最終排名。

## 2. 前置條件

- [ ] Phase 3 的房間、手機控制器、控制權驗證及斷線處理已通過。
- [ ] Phase 1–2 的駕駛、物理和 Race Core 能在不依賴 DOM／React 的環境執行。
- [ ] 已定義輸入／狀態協定版本、模擬 tick、狀態快照更新頻率及網路延遲測試方式。
- [ ] 確認獨立 Node.js 主機可長時間執行 Colyseus 與遊戲模擬。

## 3. 完整任務清單

- [ ] **P4-T01｜玩家與 Lobby**：2–4 位玩家加入、選車色／暱稱、Ready、Host 開始、退出、房間額滿提示。
- [ ] **P4-T02｜權威模擬**：同一套固定 tick 的遊戲核心移至 Node.js；伺服器處理輸入、位置、速度、碰撞、檢查點、圈數及結果；客戶端不得直接寫入座標或比賽成績。
- [ ] **P4-T03｜玩家輸入與狀態同步**：每位玩家具有獨立控制權；傳送有限頻率的 `InputFrame`，伺服器廣播位置／旋轉／速度等狀態快照及關鍵事件；避免廣播完整 React 狀態。
- [ ] **P4-T04｜渲染插值與補正**：Host 端在快照間做插值，網路不穩時限制外插與瞬移；必要時再補上控制者預測／Reconciliation，非第一版硬需求。
- [ ] **P4-T05｜玩家互撞與 Arcade 反應**：卡丁車之間有碰撞、互相推開、適當減速與短暫偏轉；高速重擊可觸發簡單 Spin Out；反應以遊戲手感優先。
- [ ] **P4-T06｜多人賽事與名次**：同步倒數、每人 CP／圈數／完成時間；伺服器依有效進度計算排名；全部完賽或達到結束條件後進入結算。
- [ ] **P4-T07｜共用攝影機／玩家可視性**：Host 使用追蹤多位玩家的攝影機，提供最低及最高縮放限制；加入玩家識別標籤。若玩家距離過遠，採清楚定義的追蹤／離場提示策略。
- [ ] **P4-T08｜斷線、重連與房間清理**：短暫斷線保留玩家席位，輸入轉為安全狀態；超時離線後依規則退出／視為未完成；最後一人離開後釋放 Room。
- [ ] **P4-T09｜2–4 人整合及壓力測試**：多手機實測同步、碰撞、公平起跑、重連與結算，記錄網路與伺服器負載。

## 4. 涉及模組

`server/rooms/RaceRoom.ts`、`server/systems/{Simulation,Input,Collision,Race,Ranking}`、`server/state/`、`game/core/`（共用）、`game/network/{protocol,interpolation}`、`game/rendering/{SharedCamera,PlayerKart,Lobby,RaceHUD}`。

## 5. 驗收標準

- [ ] 同一房間 2–4 人各用不同手機駕駛、彼此無法操作其他玩家的車。
- [ ] 所有車輛位置與排名來自權威伺服器；Client 不能偽造圈數或位置。
- [ ] 車與車、車與護欄的碰撞由同一權威模擬決定；Host 畫面不出現持續性大幅抖動。
- [ ] 每名玩家的有效 CP 與圈數獨立正確；完賽結果對所有人一致。
- [ ] 至少一次完整四人比賽可由 Ready、倒數跑到結算。
- [ ] 短暫斷線後能恢復，超時離線也不阻斷剩餘玩家。

## 6. 自動與手動測試

**自動測試**

- [ ] 伺服器單元／整合測試：多玩家輸入隔離、固定 tick、權限驗證、合法 CP、同時衝線排序、碰撞事件。
- [ ] 故意注入延遲、封包遺失、重複／過期輸入，確認更新順序與狀態收斂。
- [ ] Playwright 多 Context：Host + 2–4 個模擬 Controller，驗證進房、Ready、開賽、斷線與賽果。
- [ ] 負載測試：依預期同時房間數模擬輸入，觀察 tick 延遲、記憶體與連線數。

**手動測試**

- [ ] 2、3、4 人同場各完成至少一場，包含玩家互撞與有人落後的情境。
- [ ] Wi-Fi 混合行動網路、裝置鎖屏、切換分頁、Host 頁面重新整理和重連。
- [ ] 高速正面撞擊、斜角互撞、三車連撞、同時衝線及有人中途離開。
- [ ] 觀察共用攝影機在玩家距離很大時的可玩性。

## 7. 明確不包含的功能

完整道具系統、原創正式模型、複雜配對媒合、帳號與好友系統、跨伺服器房間遷移、排名積分、手機各自渲染完整 3D 賽事。

## 8. 風險與阻塞條件

| 風險／阻塞                                    | 處理方式                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------ |
| Rapier 在 Node／WASM 環境與前端更新結果不一致 | 由伺服器做唯一權威運算，客戶端只視覺插值；鎖定相容套件版本。             |
| 網路延遲造成碰撞抖動或車輛瞬移                | 固定 tick、輸入序號、狀態快照、插值及受控狀態修正。                      |

| 伺服器成本與部署平台不支援 WebSocket 長連線   | 使用支援常駐程序的 Node.js 主機；Next.js 與遊戲主機分開。                |

**離開本階段的門檻**：可讓四位朋友用手機加入同場，在 Host 螢幕完成一場有碰撞、圈數、排名的比賽。

# Phase 5｜道具、回饋與遊戲體驗

## 1. 階段目標

在穩定多人對戰基礎上，加入簡單但完整的派對賽車玩法，包括道具、重擊反應、Boost Pad、視覺／音效回饋與完整賽後流程。

## 2. 前置條件

- [ ] Phase 4 的多人權威模擬、碰撞與排名已穩定。
- [ ] 已定義伺服器權威事件（拾取、使用、命中、免疫、加速、重生）與客戶端特效事件格式。
- [ ] 確定道具效果不需要真實車體損傷或擬真力學。

## 3. 完整任務清單

- [ ] **P5-T01｜道具箱及拾取**：配置賽道拾取點、冷卻與重新生成；重複穿過不會無限制取得道具。
- [ ] **P5-T02｜道具背包與隨機規則**：每人先限制同時持有一個道具；伺服器依可測試的規則發放，測試時支援固定亂數種子。
- [ ] **P5-T03｜首批三種原創道具**：建議 Boost（速度增益）、Shield（一次防禦）、Projectile 或地面 Trap（攻擊）；所有命中及效果由伺服器判定。
- [ ] **P5-T04｜手機 ITEM 操作與 HUD**：手機可使用當前道具；Host 與手機同步持有狀態、冷卻及使用回饋。
- [ ] **P5-T05｜命中與 Spin Out**：道具擊中時根據類型處理短暫旋轉／減速／無法控制；提供恢復窗口，避免無限連續受擊。
- [ ] **P5-T06｜Boost Pad 與可選跳台**：在少量賽道區域加入加速帶；跳台只有在可穩定落地時才加入主線。
- [ ] **P5-T07｜視覺與音效**：輪胎煙霧、漂移火花、撞擊閃光、受擊旋轉、道具特效、倒數與完賽音效；提供音量與靜音控制。
- [ ] **P5-T08｜遊戲節奏與完整結算**：處理落後者、有人提早完賽、最後玩家逾時、賽後名次、再玩一次及返回大廳。
- [ ] **P5-T09｜平衡調整與遊戲測試**：以實際 2–4 人遊玩結果，調整道具出現、效果時長與受擊恢復，避免道具過度主導比賽。

## 4. 涉及模組

`game/core/items/{ItemSystem,ItemInventory,ItemEffects}`、`game/core/kart/{DriftSystem,BoostSystem,SpinOutSystem}`、`game/rendering/{Particles,ItemBox,HUD,FinishScreen}`、`game/input/controller.ts`、`server/systems/{ItemSystem,CombatSystem}`。

## 5. 驗收標準

- [ ] 玩家可以拾取、持有並使用道具，且不會重複領取同一冷卻中的道具箱。
- [ ] 道具效果、護盾及受擊狀態在所有玩家和 Host 畫面一致。
- [ ] 撞牆、互撞、道具受擊有不同且明顯的 Arcade 反應；玩家能在合理時間內恢復。
- [ ] 手機控制器可清楚查看及使用道具，操作時不易誤觸方向鍵。
- [ ] 完賽後可查看統一排名並在同一房間重賽。

## 6. 自動與手動測試

**自動測試**

- [ ] Vitest：拾取權限、道具持有上限、冷卻、護盾抵擋、命中與恢復、加速效果清除。
- [ ] 使用固定亂數種子，驗證掉落與重放時可以重現結果。
- [ ] 整合測試：同時拾取道具、攻擊命中與斷線、賽事結束後不再使用道具。
- [ ] Playwright：手機 ITEM 鍵、Host HUD 道具變化、重賽流程。

**手動測試**

- [ ] 2–4 人進行多場含道具比賽，檢查玩家是否看得懂攻擊來源與受擊狀態。
- [ ] 連續命中、碰撞與道具疊加、護盾與加速同時作用。
- [ ] 測試不同音量、靜音、手機按鈕大小及橫直向誤觸情形。

## 7. 明確不包含的功能

十數種道具、角色專屬技能、複雜 AI 對手、商城、付費系統、正式大量場景、線上賽季與排行榜。

## 8. 風險與阻塞條件

| 風險／阻塞                     | 處理方式                                                         |
| ------------------------------ | ---------------------------------------------------------------- |
| 道具與碰撞同時觸發造成狀態混亂 | 伺服器以明確事件優先順序處理，使用有限狀態與效果互斥／疊加規則。 |
| 攻擊效果過多讓車輛持續失控     | 加入受擊保護時間、效果持續上限及清楚的恢復提示。                 |
| 粒子及音效過多導致掉幀         | 限制同時粒子數，採重用／實例化；音效資產壓縮與音量控制。         |
| 未取得資產授權                 | 以原創或授權素材替代，不複製 Nintendo 的模型、角色、音效或標識。 |

**離開本階段的門檻**：四人能完整玩一場包含拾取／使用道具、碰撞、受擊、特效、結算及重賽的多人卡丁車遊戲。

- [ ] 已建立基礎效能量測裝置與測試情境（電腦 Host + 四台手機）。

## 3. 完整任務清單

- [ ] **P6-T01｜美術規範**：定義原創卡通風格、比例、配色、光影、角色與車輛識別；訂定資產多邊形、紋理及材質預算。
- [ ] **P6-T02｜正式卡丁車與角色模型**：以 Blender 製作原創車輛、輪胎與駕駛者；建立轉向、漂移傾斜、受擊與勝利等必要動畫；輸出 GLB。
- [ ] **P6-T03｜正式賽道與場景**：完成至少一條品質一致的正式賽道，含路面、護欄、草地、地景、裝飾和可讀的指示；確認新模型對齊既有 Collider／Checkpoint。
- [ ] **P6-T04｜模型載入與資產管理**：資產命名、按場景載入、載入／錯誤畫面、GLB 與紋理壓縮、重複物件實例化及資源釋放。
- [ ] **P6-T05｜遊戲 UI/UX 完善**：首頁、建房、大廳、車輛選擇、手機控制器、HUD、結算和設定；處理小螢幕、斷線與權限錯誤。
- [ ] **P6-T06｜3D 與網路效能**：量測 FPS、Frame Time、Draw Call、GPU／記憶體占用、同步延遲與伺服器 tick；依量測調整光影、粒子、材質和快照頻率。
- [ ] **P6-T07｜跨平台及無障礙檢查**：Host 桌面瀏覽器、iOS／Android 控制器、橫直向、安全區、觸控目標、低效能降級及感測器失敗回退。
- [ ] **P6-T08｜CI/CD、監控及安全**：Lint、型別檢查、單元、整合與核心 E2E；前後端分開部署；設定錯誤追蹤、連線紀錄、房間資源上限、輸入速率限制、HTTPS/WSS。
- [ ] **P6-T09｜Release Candidate 驗收**：執行四人完整端到端遊玩、壓力與網路干擾測試；修正阻斷遊戲問題，撰寫公開使用說明與已知限制。

## 4. 涉及模組

`game/assets/`、`public/models/`、`game/rendering/{Kart,Character,Track,Environment,Effects,Camera}`、`app/{game,room,controller}`、`game/network/`、`server/`、CI 工作流程、監控與部署設定。

## 5. 驗收標準

- [ ] 遊戲使用可公開展示的原創或授權 3D 素材，至少有一條完整 3D 賽道與足夠辨識的原創卡丁車／玩家外觀。
- [ ] 3D 車輛、碰撞體、輪胎與動畫視覺位置協調；沒有頻繁穿模。
- [ ] 正式部署網址可建房、手機掃碼、2–4 人對戰、使用道具、結算及重賽。
- [ ] 桌面 Host 在預先指定的測試機與畫質設定下，多人遊玩達到穩定目標（建議先以接近 60 FPS 作為調校方向；以實測結果記錄而非未測即宣稱）。
- [ ] 手機控制器在支援裝置上保持操作順暢，連線失敗有明確回饋。
- [ ] CI 的型別、Lint、單元與核心整合測試通過；正式環境有基本錯誤與伺服器健康監控。
- [ ] 四人完整 Release Candidate 驗收沒有阻斷流程的問題，已知非阻斷問題有紀錄。

## 6. 自動與手動測試

**自動測試**

- [ ] CI：型別、Lint、Vitest、多人伺服器整合、Playwright 主要房間／控制器流程。
- [ ] E2E：首頁 → 建房 → 四位控制器加入 → Ready → 比賽 → 結算 → 重賽；物理長路徑可以使用測試模式加速驅動。
- [ ] 資產檢查：GLB 是否可解析、引用的材質與檔案是否存在、資產體積是否超過專案門檻。
- [ ] 壓力測試：目標並發房間及玩家數、異常輸入、重複加入、斷線與房間清理。

**手動測試**

- [ ] 真實四人、不同手機與網路環境執行完整比賽至少數場。
- [ ] Host 桌面瀏覽器交叉測試、實機控制器橫直向與感測器授權流程。
- [ ] 記錄初次載入時間、FPS／Frame Time、車輛同步觀感、耗電與裝置發熱。
- [ ] WebGL Context Lost、網路斷續、音效無法自動播放、手機轉向失敗與 Host 重新整理的恢復路徑。
- [ ] 檢查著作權與資產授權、公開網站的隱私與必要操作說明。

## 7. 明確不包含的功能

全球排行榜、帳號／社群系統、季票與商城、跨地區競技媒合、數十條賽道、正式電競級防作弊、所有手機可直接顯示獨立 3D 賽事畫面。分割畫面可列為 Phase 6 後的延伸項目，**不列為本次正式上線阻塞條件**。

## 8. 風險與阻塞條件

| 風險／阻塞                         | 處理方式                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------ |
| 正式模型製作遠超程式開發工作量     | 先一條賽道與少量原創車款，重用材質與骨架，設定明確資產預算。             |
| 4 人／大量物件時 Host GPU 負載過高 | 量測後優先控制 Draw Call、貼圖大小、陰影、透明粒子及更新頻率。           |
| 手機、瀏覽器及網路條件差異         | 提供觸控備援、畫質選項、斷線提示與清楚的最低支援條件。                   |
| 長連線主機不穩、部署成本增加       | 前後端獨立部署，設置健康檢查、日誌、超時清理和容量上限。                 |
| 正式美術接入後與 Collider 不一致   | 視覺 Mesh 與遊戲 Collider 分開版本管理，針對新賽道重新跑碰撞與 CP 驗收。 |

**離開本階段的門檻**：公開網站上可穩定進行原創 3D 四人卡丁車比賽，並具備可重複執行的驗收流程與正式監控。
