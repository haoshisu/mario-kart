# 選圖載入效能（2026-10-23）

依使用者「開始下一階段」，回到 Phase 6 的載入與效能品質，先處理選圖畫面的實測瓶頸。

## 改動

原本 `TrackPicker` 為十三張卡片逐一呼叫 `getTrackData`，因此只為顯示縮圖就建立全部賽道的道路幾何、捷徑、跳台、道具與碰撞相關資料；每次渲染也會重新串接大量路徑座標。

現在 `trackPreview.ts` 使用既有中心線取樣計算相同 viewBox，直接用原創設計的三次曲線產生 SVG。每圖僅產生並快取一份預覽，選圖不呼叫完整賽道建立流程；實際場景仍在需要該圖時透過原有 `getTrackData` 快取取得。十三圖的名稱、路線、紀錄標記、選擇行為及實際幾何／權威規則皆不變，協定維持 23。

首次選擇尚未建立的地圖仍有完整場景建立與資產載入成本；本輪不新增背景 worker、動態畫質或修改物理。

## 可重現量測

分別以全新 Node process 執行：

```sh
npx tsx scripts/benchmark-track-previews.ts before
npx tsx scripts/benchmark-track-previews.ts after
```

腳本 before 分支重現原本建立十三圖＋串接折線的流程，after 使用新預覽模組。三次本機量測（不含模組載入時間）：

| 指標 | 修改前 | 修改後 |
| --- | --- | --- |
| 十三圖首次預覽資料 | 5,718–5,866 ms | 6.53–6.89 ms |
| 快取後重複取得全部十三圖 100 次 | 252–257 ms | 0.045–0.046 ms |
| 十三張 SVG 路徑總字元數 | 459,932 | 14,153 |

路徑字串減少約 96.9%。這是特定資料處理的微量測，不代表整頁加速倍率或 FPS 提升。腳本輸出的 heap 差值會受 GC 影響，不能當作精確記憶體節省量，更不是 GPU 記憶體。

## 驗證

單元測試覆蓋十三圖預覽邊界、曲線完整性、快取與字串預算，並將完整賽道建立設為拋錯，確認選圖渲染不依賴它。瀏覽器核對十三圖 SVG 長度與既有中心線差異小於 1%，以及台南／台中標準、省電與窄螢幕選圖。

修改前 production Brave 選圖可見的單次樣本為 6,891 ms（從導航呼叫至十三卡可見，含瀏覽器與載入成本）。後續與同機修改後樣本對照，不將單次瀏覽器樣本視為跨平台保證。

最終結果：同機 production Brave 修改後選圖可見樣本為 **512 ms**，修改前為 **6,891 ms**。兩次為獨立測試情境的單次本機樣本，測試順序與快取狀態可能影響數值；不能據此承諾所有裝置相同比例改善。十三張實際 SVG 長度對照通過，路徑總字元數為 14,153。

`npm run check` 通過（74 檔／649 項），production build 通過；修改前一項基準瀏覽器測試通過，修改後四項不同情境通過（約 41.8 秒，含巡遊回歸）。已檢視 [修改前桌面](../doc/images/track-preview-performance/before-desktop.png)、[修改後桌面](../doc/images/track-preview-performance/after-desktop.png) 與 [修改後窄螢幕](../doc/images/track-preview-performance/after-mobile.png)，台南與台中場景及選圖內容正常。既有依賴的 Rapier 初始化參數棄用與終端色彩警告仍存在，未觀察到新增瀏覽器執行錯誤。

本輪完成選圖載入瓶頸的局部優化，尚未部署；Windows／iPhone／Android 真機、四人長時間效能與完整 Phase 6 驗收仍未完成。
